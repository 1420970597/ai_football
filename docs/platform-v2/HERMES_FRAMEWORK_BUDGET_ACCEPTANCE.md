## 目标与执行边界

本次只扩展原有两份框架集成脚本，增加专属 Docker 运行器和九项替身契约测试。未修改业务服务、生产框架启动扩展、配置、技能、远端持续集成或任务总台账。模型提供方是明确标注的确定性替身；实际运行固定 Hermes、MCP SDK、双工作进程 API 和临时 PostgreSQL。

所有测试数据均为合成隔离记录。没有读取业务环境、调用 Telegram、乐鱼、真实模型、真实账户或交易。内部网络没有发布端口或外网出口；测试主机、端口和数据库名称被脚本校验。测试数据库只存在于本任务容器的内存文件系统。容器根文件系统及源码、配置、上下文、技能挂载均只读，框架状态在受限内存中。

各常驻服务合计最多 1.425 CPU、1696 MiB；单次验证客户端最多 0.25 CPU、256 MiB，串行运行。各容器同时设置进程预算。Hermes 使用该固定镜像的 Python 和原项目启动扩展直接执行，非 root、独立 init；这是隔离测试入口，不修改生产入口。启动、应用、数据库、单元和框架测试均在 Docker 内；宿主机只编排、冻结复制和保存日志。

## 失败保留与修正

全部失败日志保留在同一独立证据目录，不覆写为成功：

- 第一轮启动固定镜像默认 s6 监督器遇只读根文件系统退出 111；验证尚未开始。结束时旧编排信号处理未保留终止码，日志误打印 0，明确不能作为通过证据。改为非 root 直接执行原框架入口，并为信号保存 130/143。
- 第二轮挂载配置产生的父目录由 Docker 创建为 root 所有，框架无法创建状态目录；主动终止后真实退出 143。将测试状态 tmpfs 精确挂到框架主目录，保留配置只读。
- 第三轮正常 260 场通过，但恶意游标预期写为 400；实际现有 next-cursor 契约在更早校验阶段拒绝为 409，退出 1。断言按真实契约修正，没有修改业务代码或取消拒绝验证。
- 第四轮按原请求名称匹配未知工具错误，未考虑框架工具名称纠正以及英文 does not exist，退出 1。替身以调用编号关联原请求与实际名称，保留拒绝检查。
- 第五轮全部主场景和重启通过，但误把最多四回合等同提供方总计至多六请求；框架另有辅助和两次收尾，共七请求，退出 1。改为四次实际技能结果、总请求仍有界不超过七。
- 第六轮九项单元及全部五个框架场景退出 0。最终又补一次伪造比赛编号拒绝，重新冻结并完整重跑，不沿用前轮结果覆盖新增场景。
