# Hermes Transient Retry Durability

Status: implementation written; 63 focused worker/classification tests pass in Docker with task-owned PostgreSQL; scheduler/admin and full API regression checks pending.

| Field | Evidence and decision |
| --- | --- |
| Goal | Keep a current expert message eligible for review when Hermes' configured provider temporarily rate-limits or returns server errors, then automatically resume after the provider recovers. |
| Responsibility | `services/api/app/worker.py`, review worker tests and deployment of review-worker containers only. |
| Prerequisites | E189 provider failure classification and short Hermes framework failure path are active. The fixed model route and provider configuration stay unchanged. |
| Current evidence | Watch-03 ran 1800.4 seconds / 55 samples. It recorded 208 `HermesProviderUnavailable` failures at `model_review`, average 4214.3 ms / P95 5719.7 ms, zero Hermes results and zero review receipts. The configured provider returned HTTP 429 and 503. Of 12 new real-time jobs, 3 became failed at attempts=5 due to `HermesProviderUnavailable`, 7 remained retry, and 2 old revisions stopped as `source_edited`; no missing job observations occurred. |
| Gap | `process_job` marks every retryable failure failed once attempts reach `MAX_ATTEMPTS`; `_claim_from_lane` also excludes jobs at that limit. A provider outage longer than the attempt schedule therefore turns a recoverable review into a permanent stopped job. |
| Decision | Keep `provider_transient`, `timeout`, and `network` failures in durable `retry` state beyond the ordinary five-attempt limit. Increase exponential backoff from 60 seconds to a 900-second cap and use bounded 0-60-second jitter. Claim beyond the limit only when the same current `attempt_id` has a `review_failure` trace marked retryable with one of those categories. Keep the five-attempt dead-letter behavior for permanent failures, unrelated retry classes and expired leases without a matching failure trace. No schema migration is needed because `v2_analysis_traces` is indexed by `(job_id, sequence_no)`. |
| Actions | Add a shared SQL eligibility predicate for pair selection and row claim; update failure state handling and delay calculation; add unit coverage for capped backoff and temporary-PostgreSQL coverage proving a fifth-attempt provider failure remains claimable as attempt six. Retain assertions that permanent media errors and expired final leases still dead-letter and that failed provider attempts create no model result, signal or receipt. Run the focused worker and scheduling suites in Docker, then the API test suite in the task-owned test database. |
| Acceptance scenes | A retryable provider failure at attempt five remains `retry`, carries the matching attempt trace, receives a capped/jittered future `available_at`, and can be claimed as attempt six after the delay. A permanent visual-input error remains failed. An expired final-attempt lease without a retryable trace remains failed. A superseded message stays unclaimable. Existing real-time fairness, expert concurrency and no-false-receipt tests pass. |
| Failure handling | If the trace does not match the current attempt, do not bypass the attempt limit. If the isolated regression fails or claim queries regress, do not deploy. Preserve the watch-03 failure evidence and all user data; after worker activation, start a fresh 1800-second observation and count only `real_time` jobs with current-message receipts as successful. |
