# Hermes Transient Retry Durability

Status: implementation and Docker isolation verification passed; 65 focused worker/classification tests and 1202 full API tests pass. Both review-worker replicas run E190a. Watch-05 completed but failed runtime acceptance because the configured provider continued returning transient failures; jobs remain durably retryable.

| Field | Evidence and decision |
| --- | --- |
| Goal | Keep a current expert message eligible for review when Hermes' configured provider temporarily rate-limits or returns server errors, then automatically resume after the provider recovers. |
| Responsibility | `services/api/app/worker.py`, review worker tests and deployment of review-worker containers only. |
| Prerequisites | E189 provider failure classification and short Hermes framework failure path are active. The fixed model route and provider configuration stay unchanged. |
| Current evidence | Watch-03 ran 1800.4 seconds / 55 samples. It recorded 208 `HermesProviderUnavailable` failures at `model_review`, average 4214.3 ms / P95 5719.7 ms, zero Hermes results and zero review receipts. The configured provider returned HTTP 429 and 503. Of 12 new real-time jobs, 3 became failed at attempts=5 due to `HermesProviderUnavailable`, 7 remained retry, and 2 old revisions stopped as `source_edited`; no missing job observations occurred. After the first E190 deployment, read-only task audit found 96 failed real-time jobs (attempts=5) whose current attempt trace proves retryable `provider_transient`, all within the 24-hour real-time window. E190a watch-05 completed 1803.0 seconds / 55 samples, with API health/readiness 200 for every sample, zero missing-job observations, and `telegram_all_healthy=false` due intermittent `lease_deferred` and `reconciliation_deferred` states despite all six leases remaining active under one owner. At the exact watch end, 216 `provider_transient` failures had occurred, with zero Hermes result traces and zero receipts. A post-window Docker audit found 15 ready real-time messages posted during the watch: 11 were retrying at attempt 3, 2 at attempt 4, and 2 at attempt 5; all had current-attempt `provider_transient` evidence and no receipt. Two further unsupported posts had no job. Another 34 ready messages created during the watch were historical replay of older posts and correctly remain outside real-time acceptance. Post-to-event persistence for the 15 real-time messages averaged 7.38 seconds, P95 16.11 seconds and maximum 17.57 seconds; only 1 of 15 was within 3 seconds. A filtered 30-minute Hermes log count included 1464 mentions of HTTP 503 and 56 of HTTP 429. A read-only audit showed 120 eligible long-running real-time provider jobs (attempts 6-8) still in `retry`; E190a prevented them from becoming terminal failures. |
| Gap | Before E190, `process_job` marked every retryable failure failed once attempts reached `MAX_ATTEMPTS`, and `_claim_from_lane` excluded those jobs. E190 made new real-time transient failures persistent, but already-failed rows remained terminal, so they also need recovery. |
| Decision | Keep `provider_transient`, `timeout`, and `network` failures in durable `retry` state beyond the ordinary five-attempt limit. Increase exponential backoff from 60 seconds to a 900-second base cap and use bounded 0-60-second jitter. Claim beyond the limit only when the same current `attempt_id` has a `review_failure` trace marked retryable with one of those categories. Also reclaim pre-E190 `failed` rows only when they are in `real_time` mode, remain within the real-time posting window, and carry that exact current-attempt transient trace. Keep historical replay, permanent failures, unrelated retry classes and expired leases without a matching failure trace closed. No schema migration is needed because `v2_analysis_traces` is indexed by `(job_id, sequence_no)`. |
| Actions | Add one shared SQL eligibility predicate for pair selection and row claim; update failure state handling and delay calculation; add temporary-PostgreSQL coverage proving a fifth-attempt provider failure remains claimable as attempt six, an already-failed current real-time provider row resumes, and historical/permanent/mismatched-trace rows stay closed. Retain assertions that failed provider attempts create no model result, signal or receipt. Run the focused worker and full API suites in Docker with the task-owned test database. |
| Acceptance scenes | A retryable provider failure at attempt five remains `retry`, carries the matching attempt trace, receives a capped/jittered future `available_at`, and can be claimed as attempt six after the delay. A prior terminal failed real-time job with the same current-attempt trace resumes; a historical replay and permanent visual-input failure remain failed. An expired final-attempt lease without a retryable trace remains failed. A superseded message stays unclaimable. Existing real-time fairness, expert concurrency and no-false-receipt tests pass. |
| Failure handling | If the trace does not match the current attempt, do not bypass the attempt limit. If the isolated regression fails or claim queries regress, do not deploy. Preserve the watch-03 failure evidence and all user data; after worker activation, start a fresh 1800-second observation and count only `real_time` jobs with current-message receipts as successful. |
