# E516：模型请求耗时的隔离兼容实验

更新时间：2026-11-07 05:39 UTC。状态：研究中，尚未修改应用或线上请求配置。

- 目标：找出真实图文审核的模型耗时占比，验证可控推理开关是否减少耗时且保留图文理解；三秒目标仍须按接收至当前系统回执验收，不能用单次调用代替。
- 责任目录：integrations/hermes负责框架请求；services/api仅保留原审核和权限合同；tests负责固定框架及图文行为验证。前置依赖为现有deepseek-v4.1-flash、固定Hermes版本、当前视觉和工具白名单。
- 当前证据：E503短文本provider调用3745.003ms、10582输入token；图片新推荐累计provider调用102823.278ms、116976输入token、排队55200.405ms；旧单图片反馈40601.25ms。原始trace为累计框架调用，不误称单个上游生成。实际框架会话存在reasoning_content，但reasoning_tokens统计为0，不能以零统计证明未推理。
- 缺口：custom路由是否实际发出/接受禁用推理参数、固定上下文及工具定义的重复成本、禁用推理后的视觉/歧义正确性尚无证据。现有框架源码支持reasoning_config与extra_body_additions，但不能由此推断当前网关兼容。官方公共文档检索本次返回400/endpoint不支持，不把检索失败当上游模型配置事实。
- 设计及动作：先在Docker读取固定transport构造结果，只输出字段名/推理开关/耗时与token数；仅用无业务的合成短文本做有界兼容探针，不提交真实job、信号或订单。若实际wire无差别则不发无意义重复请求。参数有差别且被支持后才设计成对图文语义验收，不在得到准确性和权限证据前改线上配置。
- 验收：真实请求无参数错误、思考输出和token观测自洽；图文原名/期间/盘口/方向、反馈排除、多比赛、歧义、视觉失败及注入行为不退化；固定全套和候选同源通过后才能受控切换。保留provider错误与全量窗口漏审/排队证据，不以缩短超时丢任务实现目标。
- 失败处理：兼容失败仅停止该参数实验，保留原模型/配置；不改路由、放宽绑定或生成假结论。真实业务观察E514继续。凭据只在Hermes保护环境中，秘密/完整请求/图片base64不输出。

06:24阶段：两种合成请求均37token、无推理输出，3508.916/3560.046ms，未证明关闭推理加速，因此不改线上。下一步仅追加最多两次相同合成短文本的HTTP连接跟踪，记录事件名及耗时，不记录headers/URL/body/密钥；使用同一客户端比较首次连接与复用，区分连接阶段与响应头等待。非流式响应头等待包含网络和上游处理，不能直接称为模型首token时间。原MCP/图文/业务请求不变。
