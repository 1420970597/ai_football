# 故障与恢复闭环验证

日期：2026-10-27。所有故障仅作用于临时内部 Docker 网络、临时 PostgreSQL、确定性 Telegram/模型/S3 替身。未对生产数据库、对象存储、Telegram 或模型注入故障；未提交实盘订单。

## 新增隔离场景

专用测试：`tests/test_fault_recovery_matrix.py`。不把 HTTP 200 或错误分类单测当作恢复成功，必须检查持久状态与唯一性。

| 故障 | 注入位置 | 必须通过的恢复与无重复断言 |
| --- | --- | --- |
| PostgreSQL 实际连接中断 | 已在服务器执行事务内 `pg_sleep` 的连接，由临时管理员通过精确 PID 与独立数据库名终止 | Telegram 写返回 503、写入未确认、不自动重放；事务和检查点全部回滚；连接池重建连接后重放同事件只产生一份原文、事件和审核任务 |
| S3 上传超过整体截止，线程迟到 | 使用真实采集媒体验证/哈希/候选登记流程，阻塞 `boto3.put_object` 替身，业务持久层为真实临时 PostgreSQL | 截止后 failed、候选在库且任务数为 0；迟到写入不得改 ready；重试同内容哈希/对象键恢复 ready；再次重试仍只一条原文、一条事件、一个审核任务 |
| Telegram FloodWait 60 秒 | 官方异常类型由某一群组历史流首次抛出，只替换采集模块时钟 | 其他群组持续推进；59.999 秒不发请求；60 秒恢复且只接收一次；再次轮询不重复、检查点保留 |
| 模型 429 | 审核工作器的模型调用边界首次返回带 429 响应的异常 | 真实工作器持久化退避、释放租约，截止前不能重领；持久截止推进后新 attempt 接管；通过真实搜索、消歧、读盘口及记录接口接受唯一推荐和报价证据；两次框架会话清理 |
| MCP 记录已提交但应答丢失 | 真实 MCP SDK 调用真实业务 API 并提交临时 PostgreSQL 后，传输层丢弃首次应答 | 首次明确工具超时而非假成功；数据库已有一条记录；再次相同调用得到 duplicate，同一信号与报价证据仍各一条 |
| 断连被接口异常遮蔽 | `InterfaceError` 的 cause/context 含明确 PostgreSQL 连接异常 | 仅有界 8 步防环的类型证据转 503；普通接口错误、仅有“连接已关闭”文字、环或超出边界保持 500；写入未确认、不自动重放、秘密不回显 |

模型重试测试推进的是临时数据库中的可重试时刻，不修改工作器退避计算，不实际等待数秒；TG 使用单模块时钟，不修改 asyncio 时钟。MCP 模型与 S3 服务均为替身，不声称真实上游经历了故障。DB 场景是实际 PostgreSQL 连接被终止，不是抛出异常替身。

## 已保留失败

1. 初始测试运行器网络别名不一致：5 项中数据库场景在连接阶段失败，退出 1；修正为临时 PostgreSQL 的显式同一别名。日志 `initial-runner-alias-failure.log`。
2. 首次实际断连验证发现业务缺陷：连接错误被事务清理阶段的 `InterfaceError` 遮蔽，API 返回 500，5 项中仅该场景失败，6.601 秒、退出 1。日志 `disconnect-interface-failure.log`。现已最小修复为有界且仅依类型的异常链识别。
3. 并行盘口空线增量变更尚未完整时的冻结快照：7 项中的 MCP/模型记录遇到冲突目标与索引不匹配，6.530 秒、退出 1。日志 `concurrent-null-line-schema-failure.log`。不修改断言掩盖迁移差异；等待该变更完整冻结后重跑。

上述日志位于 `.runtime/fault-recovery-20261027/`。它们是实际失败记录，不被后续通过结果覆盖。

## 最终验证

合并命令：`sh .runtime/fault-recovery-20261027/run.sh`。运行器为每次创建独立内部网络和固定摘要 PostgreSQL16，CPU 0.35/256MiB；验证器 CPU 0.5/384MiB，挂载本项目只读后复制源码冻结，不重建共享镜像。依次执行新矩阵、数据库异常、错误脱敏回归；`set -e` 保留原失败退出码。

最终命令（退出 0）：

```sh
sh .runtime/fault-recovery-20261027/run.sh > .runtime/fault-recovery-20261027/frozen-suite-final.log 2>&1
```
