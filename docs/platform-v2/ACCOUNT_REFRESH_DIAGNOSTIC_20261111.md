# 用户账户刷新异常只读诊断

更新时间：2026-11-11 08:13 UTC。

## 工作包：区分账户登录异常与平台对账失败

- 目标：解释用户指定账户在官方App登录正常、平台却显示异常的原因。
- 状态：真实只读联调通过（诊断）；业务修复未在本工作包实施，账户问题未标记已修复。
- 责任目录：`docs/platform-v2/`；业务定位范围为现有API账户状态、执行器只读协议及网页账户状态展示。
- 前置依赖：现有本人账户绑定、受保护会话、本机业务库只读TLS连接、现有远端执行器与SSH链路。
- 设计决策：仅查询指定账户的状态和有界任务记录；只在内存中流送该账户现有场馆会话，执行一次余额GET；不输出凭据、余额、订单编号或原始响应，不发起登录、续期或交易。
- 验收场景：精确匹配一名用户；核验账户与任务状态不同；实际余额读取可用；核对线上执行器的失败传播及网页状态优先级；保留现有未提交账户修改。
- 失败处理：来源拒绝时保留类别并停止额外探测，不通过强制改健康状态、清空错误或重新绑定掩盖故障。

5. 网页按最近非history任务优先展示状态：即使账户仍为`healthy`，最近刷新`failed`也会显示“校验失败”；因此用户看到的异常与官方App正常登录并不矛盾。

## 原因与处理方向

既有真实逐笔只读响应已经把`0403001`的中文原因核验为“网关限流”，见`AUTO_BETTING_PROGRESS.md`的账户刷新阻塞研究。本轮没有为取得相同拒绝再重复查单；当前余额成功、完整历史快照、自然刷新错误码、两笔对账计划及线上代码共同吻合已有根因：同账户逐笔重复扫描历史容易触发网关限流，单笔查单拒绝又连带使整次账户刷新失败，成功余额不写回，页面优先呈现失败任务。

当前证据不支持账户被封、密码错误或整个场馆会话失效的判断。仍需在独立账户工作包完成：同账户多订单共享有界历史扫描；对账失败与有效余额分开处理；保留失败订单及敞口；最终余额再次成功才推进账户校验时间；页面分别说明余额有效性和对账失败。现有两项完整CI账户失败也属于这一工作包，不能直接将未提交补丁视为已验证或已上线。

本轮业务数据库写入、登录、续期、下注、部署均为0；只提交诊断与进度文档。私有原始查询及摘要结果保留在模式700的任务目录，未将账户标识、秘密、金额或原始订单记录入Git。
