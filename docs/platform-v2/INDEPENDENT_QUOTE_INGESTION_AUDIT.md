# 比赛与盘口独立单调入库

日期：2026-10-27。本轮由主线真实观察发现，非产品完整交付声明。范围仅为批量事实入库与独立 PostgreSQL 行为测试；不改变采集网络、登录、盘口解释或正式赛果来源。

## 根因与修复

旧逻辑只遍历比赛元数据 UPSERT 返回的 accepted 行处理其报价。因此比赛源时间旧于已存比赛时，即使其报价 ctsp 较新，报价也不会参与自身单调更新。

修复将两类时间域分开：比赛仍按自身源时间决定是否更新，报价不再以父比赛更新成功为前提。比赛 UPSERT 后，通过批内 source_id 查询已有稳定系统编号及当前阶段，并在同一事务中按 source_id 排序持有行锁，所有批内报价按各自源时间进入既有单调 UPSERT。请求传来的另一 id 不能替换已有 source_id 的真实编号。

关闭缺失盘口仍只允许 accepted 的完整父快照执行。旧完整父快照可以带来更近的单项报价，但无权依据自己的缺项清单关闭其余盘口。新父元数据也无权回退较新的单项报价。

终态保护在比赛 UPSERT 条件实施：finished、cancelled 不得被 scheduled、live 回退；live 不得退回 scheduled。已有终态比赛收到更近报价时，报价仅以 closed 状态保留，旧报价也保持关闭。比赛行锁与既有正式赛果入库采用相同保护边界，等待在途赛果提交后必须读取实际终态，不能复用先前活跃状态重开盘口。正式赛果修订仍由原赛果台账处理。

## 返回契约

accepted 与 ignored_stale 继续只描述父比赛快照。旧父、新报价场景可以返回 accepted=0 且报价实际已按自身时间写入，不能把这个返回值描述为“任何数据都未写入”。本次保持现有调用者类型和计数契约，不谎报比赛更新。若上层刷新回执需要单独报价写入数，应新增明确计数而不是改变 accepted 含义；读取报价及其真实源时间是最终新鲜度证据。

## 隔离场景

新增六项 PostgreSQL 场景：

1. 旧父、新报价：保留比赛编号、源时间、比分，更新原报价编号对应的新价格；不信任另一传入比赛编号。
2. 新父、旧报价：比分和比赛源时间更新，报价价格与源时间不回退。
3. 旧完整父快照：更新现有新报价，但缺失的另一个盘口保持活跃。
4. 已完场父：更近滚球父和新盘口均不能重开，报价全部关闭。
5. 已滚球父：更近赛前父不得回退阶段，仍接受独立新报价。
6. 并发正式赛果：另一连接先持比赛锁写完场并关闭盘口，在途采集确实阻塞；释放后采集读取终态，不能重新开放任何报价。
