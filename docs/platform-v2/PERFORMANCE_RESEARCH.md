## 各功能发现

- Telegram 多群组同步已按最多 3 个群组并行，并有消息检查点、断线补偿、媒体限额及有限重试；进一步增加群组或媒体并发会提高 FloodWait、租约超时和对象存储拥塞风险。需要继续按群组分别测量源消息至持久化、历史追补年龄和媒体上传分位数，再按源端额度调度。
- 乐鱼实时 WebSocket 已记录源滞后、队列等待和投递年龄分位数，并保留受限 HTTP 轮询兜底。当前刷新器明确限制单个上游刷新、同赛事合并和请求间隔；并发触发多个过期赛事会收到 busy/throttled。不能在业务层并发打穿此限制，应先取得来源端支持批量盘口读取或经过授权的 QPS 证据。
- 审核工作器已有数据库通知和 1 秒轮询兜底，当前配置为总并发 2、历史并发 0。扩容会增加模型网关和 PostgreSQL 的同时负载；在没有提供方限流/并发容量数据时不提高并发默认值。
- 图片读取在独立并发槽中执行，当前图片准备分位数很低。保留类型、大小、哈希和总像素校验；模型的视觉理解发生在 Hermes 请求中，因此图片下载很快不代表视觉分析已完成。
- MCP 工具是可直接优化的主要串行点。原来每个同尝试工具调用都对审核任务行取更新锁，多个安全调用只能依次进入；开启并行后还会有追踪序号竞争。改为任务行共享锁，并以每任务 advisory transaction lock 原子分配证据序号；同游标仍通过原行锁拒绝并发重复分页。
- 结算计算在已取得原生比分后的写入很快：本次两条线上记录从比分观测到各自结算提交约 0.47 秒和 0.55 秒。之前不能结算的实际断点是迁移后未刷新运行角色的新表权限；受控刷新后远端工作器成功写入比分及不可变结算。订单数保持为 0。
- 页面以 1440px 和 390px 浏览器完成登录、阶段切换、推荐详情、原文/模型结果与两条真实结算点击验证。该验收证明交互正确，不提供页面加载的线上分位数；后续需要前端导航与 API 请求的独立计时。

## 已实施的优化

Hermes v0.22.5 的调度器会按 `supports_parallel_tool_calls` 并发安排同一服务器工具，但同一 MCP 客户端连接的所有 RPC 又受单一 `_rpc_lock` 保护。固定框架集成测试曾在两个独立 `resolve_match` 数据库区间上插入 500 毫秒延迟，确认同一服务器别名下实际没有重叠；所以只设置开关不能得到并行收益。

已改为两个同权限、同工具白名单但连接隔离的 MCP 名称 `football` 和 `football_parallel`，每个名称有独立客户端会话及锁。技能要求每批最多两项互不依赖的调用，分别路由到不同会话；更多调用分批，同一个 search_key 的分页仍按游标依序完成。可见工具定义从原本 6 项变为 10 项（含两个只读技能工具），新增的工具描述会增加模型输入；真实 token 成本尚待运行配置切换后的样本核算。API 中同审核尝试的有效工具请求改用共享任务行锁，完成/撤销仍会等待在途请求。证据序号使用事务级 advisory lock，保证并发追踪与分块快照的序号唯一、连续。针对同搜索游标的并行翻页仍由数据库串行化，第二个旧游标请求返回冲突；不会返回缺页或重复页。

隔离 PostgreSQL 已有独立搜索、独立盘口读取、重复游标冲突和证据快照重放并发测试。另增加不同比赛的并发录入测试，要求两项均被接受、无重复推荐、证据序号连续且快照可完全重放。固定 Hermes v0.22.5 框架隔离验收已通过 normal、adversarial、length、parallel 和四回合预算场景；在两个独立连接上并发发起不同比赛消歧，数据库每次写入前注入 500 毫秒等待，两个执行区间的重叠断言通过，所有 260 个候选完整回放，目标推荐精确接受一次。此为确定性隔离证据，不能折算成线上 P95 改善。工具定义增加带来的真实输入 token 成本须与工具延迟收益一起测量。
