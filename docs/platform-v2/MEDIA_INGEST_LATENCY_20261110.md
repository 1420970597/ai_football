# Telegram 图片就绪延迟

更新时间：2026-11-10 07:25 UTC。状态：研究中，未改业务实现。

目标：缩短真实图片消息接收至完整媒体审核任务可领取的时间，并保持远端证据登记、对象恢复与消息版本校验。责任目录 services/collector、services/api、infra、tests、docs；依赖现有授权Telegram/S3/远端数据库、任务租约及不输出秘密的真实阶段证据。

当前证据：E2811新图片8ca26dba原发帖06:58:40、接收41.254、job创建46.635、领取轨迹47.918；媒体就绪前5.381秒，真正job等待约1.283秒。旧queue_wait_ms从消息持久化起算，包含媒体准备，不能直接叫调度排队。E2812同窗口146074字节图片日志：下载432.4ms、校验4.4ms、pending登记2254.1ms、S3上传62.0ms、ready提交2169.5ms。日志没有消息编号，只能说明该时间/字节样本，后续须保留关联局限。三次只读DB往返233–468ms，DB时钟在客户端请求区间内，无改写时间依据。

缺口：当前媒体登记请求经远端bridge到本机API，再往返远端DB；需要量化HTTP转发、事务和业务SQL各占多少，先排除锁等待/连接重建。两次提交分别负责上传前的恢复清单和上传后的完整就绪/任务投递，不得为了延迟直接删除一项或把不完整图片送Hermes。

设计研究：优先核对现有事件快速事务是否覆盖媒体pending/ready更新、每次实际数据库轮次与锁等待；若有可合并的独立读取，在同一个原事务中复用；也评估API受限入口靠近远端DB的方案，须独立最小权限角色/路由，不扩展Hermes受限角色权限，不搬迁全部采集或暴露账户。保持首次登记成功前不确认检查点，上传失败有可恢复清单，旧版本/删帖/租约失效不能置ready。

实现动作：先记录同来源新图片的接收/媒体/领取/原生接收计时，使用具名隔离DB与延迟代理重现多次WAN往返，比较原事务和候选；有明确收益且全部恢复/并发边界通过后才改源码、冻结完整回归与真实发布。当前独赢collector候选冻结和发布阶段不得掺入未验证效率修改。

验收：同一文字/图片/相册内容与SHA不变；多群并行不过量占用槽位；单图/多图、下载/上传/DB失败、提交成功但响应丢失、取消线程、消息编辑/删除、群组停用和租约更换都不丢文本、不提前审核、不跨版本复用；比较端到端中位/P95/最慢及原生命令退出码，不只报告微基准。生产不写测试消息/推荐/订单，用户实盘配置保持，历史不补投。

失败处理：保留原输入和失败码，恢复对应验收未完成；候选若只减少校验、延长TTL或隐藏慢样本则否决。没有自然可接受订单时，十秒保持未验收；不把媒体局部加速称全部专家功能正常。
