| Field | Evidence and decision |
| --- | --- |
| Goal | Bound a provider outage to one model attempt per durable review attempt so the review worker can persist a retryable failure and release its lease promptly. |
| Responsibility | `integrations/hermes/` and Docker-only integration acceptance under `tests/integration/`. |
| Dependencies | Pinned Hermes `v0.22.5` image, existing configured visual model route, Hermes provider fixture, E189 worker's durable `provider_transient` retry classification. |
| Current evidence | E189 first 1800-second observation had 17 `provider_transient` attempts, zero successful Hermes results and zero MCP traces; sampled failures took about 304 seconds. Running Hermes config resolves to `api_max_retries=3` and `auto_recovery_cycles=5`; its fixed recovery ladder is 15/30/60/60/60 seconds. The second observation was stopped after about 266 seconds when this framework setting became a testable cause; its messages were historical replay, not live expert posts. First isolated run with candidate config proved normal visual review, 260-candidate pagination, adversarial input and parallel tools still pass, but the exact-one-attempt assertion failed at two upstream requests. After bounding the documented framework recovery behavior, the full rerun passed: provider 503 made 2 requests 77.8 ms apart, `review_message` raised `HermesProviderUnavailable` in 368.7 ms, with zero MCP traces, fixture bindings, signals or analysis traces. |
| Gap | The provider route remains externally overloaded. A fast framework failure must still surface as a retryable HTTP error or `finish_reason=error`; it must never be accepted as model analysis. No current real-time Telegram post or successful production-provider response was observed in these windows. |
| Decision | Set the minimum API retry setting and disable Hermes' long in-turn automatic recovery. The pinned framework also has a bounded one-shot client/credential recovery path, so the candidate must prove no more than two provider requests; the durable review job retains subsequent retries, attempt traces, 60-to-300-second backoff, and lease release. Do not change the model, endpoint, provider key, image support, or MCP policy. |
| Actions | Keep the two bounded settings in the fixed project config. The isolated provider fixture returns a controlled 503 for one review and exposes only its attempt count. Integration acceptance verifies at most two provider requests, a bounded completion time, no MCP/recommendation writes, and an HTTP/provider-error or `finish_reason=error` result. Docker verification passed; next inspect active review leases, restart only Hermes after in-flight calls drain, verify the effective config and ready health, then start a fresh full observation window. |
| Acceptance scenes | Normal visual multi-page match review still completes and records exactly one fixture signal; controlled provider 503 completes within 15 seconds, makes at most two provider requests, invokes no MCP tools and writes no signal; the application client or worker classifies the failure as retryable without a success receipt. Existing adversarial, length, parallel-tool and readonly-skill scenarios remain passing. |
