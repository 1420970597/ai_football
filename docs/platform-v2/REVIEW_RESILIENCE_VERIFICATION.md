# 审核故障分类与恢复证据

更新时间：2026-10-26。仅使用项目内隔离 Docker 和合成数据库，不连接 Telegram、乐鱼、S3、模型网关或资金接口。

## 本次实现

审核工作器继续使用既有租约、指数退避、五次尝试上限、失效租约回收和管理员幂等重审。新增内容只记录有限故障类别与耗时，不保存异常正文、请求头、令牌或远端地址：

- 超时、网络错误和模型服务暂时性 HTTP 状态归为可重试类别。
- 认证拒绝、视觉输入不合法、模型内容过滤和永久服务拒绝归为不可重试类别。
- 不可重试类别直接进入 `failed`，可重试类别才使用指数退避；不会用重试次数掩盖永久拒绝。
- 每次失败增加 `review_failure` 轨迹，记录类别、是否可重试、尝试次数和总耗时；原有 `last_error` 异常类名保持兼容。
- 领取轨迹记录消息排队等待毫秒数，成功轨迹记录模型总耗时；不把模型自由文本当成功判据。
- 失效租约或数据库不可用时轨迹写入失败会被吞掉，避免覆盖原始失败或阻碍会话清理。

## 隔离验证

1. `docker run ... python -m unittest -v tests/test_review_failure_classification.py`：2 项通过，退出码 0。覆盖超时、网络、429、认证、视觉输入和租约失效，断言不会回显秘密文本。
2. `sh infra/test/run.sh`：修改永久失败策略后需重新执行完整冻结回归；此前基线为410项、0失败、0错误、0跳过、173.823秒，退出码0。覆盖公平调度、锁竞争、租约续期、死信、管理员重审、媒体输入、恢复和账户回归；超时与视觉用例同时检查`review_failure`轨迹。

## 尚未完成

Hermes 内部工具调用的逐工具耗时仍由框架返回协议决定，当前只记录审核总耗时；总截止时间仍由工作器的 `REVIEW_TIMEOUT_SECONDS` 控制，未宣称已经与框架内部回合预算动态协商。真实模型 429、S3 超时、Telegram FloodWait、数据库短断和订单回执丢失尚未做真实上游注入；这些属于后续故障演练，不用合成结果替代。
