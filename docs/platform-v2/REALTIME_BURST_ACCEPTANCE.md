# E504：有界接收背压与逐帧调度

更新时间：2026-11-07 04:17 UTC。状态：研究中，隔离复现成立，设计已记录；尚未修改或部署collector。

- 目标/责任：services/collector实时接收与tests行为验收，消除单帧同步入队在消费者可用时仍丢事件的调度缺陷；不混入模型/下注/结果适配。依赖已核验的原生C103/C105等事件形状、当前128容量及串行上传合同。
- 当前证据：E500五分钟真实只读采样中，WS发生一次额外重连，累计丢弃195→408、队列最高128、投递失败0；这证明现场拥塞，不单独证明现场帧大小。隔离使用现有push_events解析300条不同比赛C103原生形状，消费者回调立即成功；现有同步循环仍仅送达128、丢172、重同步1。命令在Docker固定验证器执行退出0，e504-before-burst.json保留；不把隔离300条说成实际线上单帧。
- 缺口/设计：同一帧共享最多2秒入队等待预算；队列满时await有界put，让消费者运行；预算耗尽仍按原计数丢弃并触发重同步。队列保持128（现有自定义硬上限256不变）、消费批次100、1MiB帧上限、15秒报价期限、5/12秒心跳及串行上传/公平性均不变。不得逐事件各等2秒，不能静默覆盖独立盘口或改写源时间。记录帧事件最高数、背压等待/超时与等待总毫秒，保持标量计数，不记录载荷。
- 实现动作：复用一处入队结果统计，新增有限异步逐帧准入并在真实接收循环使用；保持原同步辅助方法与溢出/重同步契约。增加原生大帧快速消费者、不同市场变更、阻塞消费者共享截止、取消put不留幽灵事件、正常心跳和订阅维持的行为验证。验证期间冻结代码，先定向再独立冻结全套、同源候选、仅collector排空租约切换。
- 验收场景：300条独立原生事件经实际run循环全部送达且0丢失；排队上限保持、源/接收时间不变、独立变更不合并；消费者阻塞时单帧等待不超过共享预算、丢弃精确且恢复触发重同步；取消不留下待put任务或事后入队；重连/权限/限流/消费者故障原契约仍通过。发布后完整30分钟六源TG逐帖对账、盘口队列与新鲜度同口径观察，不能以隔离结果替代真实改善。
- 失败处理：任何无限等待、错误计数、心跳退化、遗漏不同市场或现有测试失败均停止上线，保留原失败再定向修复；门禁或新租约失败仅回滚collector镜像，不回滚持久化数据，不触碰授权执行器。即使本修复通过，DB往返/模型耗时/上传拥塞仍可能导致三秒失败，须如实保留。
