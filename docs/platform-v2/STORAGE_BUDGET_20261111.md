# 三天热数据与30–50 GB容量评估

更新时间：2026-11-11 01:46 UTC；基线9fa93e96，分支fix/TASK-78-hermes-telegram-sync。

目标：以现有实际占用和增长率评估仅保留三天比赛/TG热数据、长期保留专家决策与统计后，能否控制项目总盘30–50 GB。责任目录infra/recovery、docs、现有数据库/对象存储只读证据。前置依赖：远端当前表大小、索引、TOAST、对象前缀、日志、WAL、开发副本和备份归属；统计依赖的最小原始证据必须保留。

当前证据：本机项目.runtime约26G、reports约4.1G、output约30M、.git约115M（du -sh退出0）；宿主根盘88%/31G可用。Docker全机含其他项目images46.33GB、containers11.5GB、volumes53.5GB，不能全部归因球讯。历史保留演练只允许具名隔离库且下限30天，尚无生产三天自动清理；不得改其门禁冒充已支持。已有专家信号、报价证据、结果、结算和原文外键，不能直接按日期删除被引用的赛事/TG。

工作步骤：读取当前关系/媒体/文件元数据，采样短窗增长和引用；给出热层、长期证据、备份/维护空间、开发资源分别预算；记录可删/不可删边界与迁移/恢复验证路径。验收：使用真实采样和明确计算，未知项保留未知，区分逻辑删除可复用空间与返还文件系统，不把估算或集群总量写成项目精确值。失败记录类别与原退出码，不使用零填补；本轮不执行生产删除、VACUUM FULL、迁移或对象生命周期变更。

阶段记录：01:35–01:42 UTC完成关系大小、窗口、引用与开发副本测量；以下为完成后的研究结果。状态为“设计已记录，生产容量验收未通过”，不把报告完成写为三天留存已上线。第二项一键实盘下注/金额配置会直接促成赌博交易，本轮不实现相关接口或套餐交易授权；不修改用户开关、资金配置或此前未提交代码。

## 一、结论与口径

新版运行热盘控制在30–50 GB是合理的工程目标；**仅设置比赛/TG三天留存，不能让当前整套占用降至这个范围，也不能保证无限历史始终不超过50 GB**。

最主要的问题是仍共存在同一个数据库内的旧模型数据，其次是开发副本和测试资源。新版无需逐秒永久保存全站比赛过程与全部盘口变化，但必须保留能够重建推荐解释、分体育项目统计和结果修订的最小证据链。仅存一条解析结论和可变正确率计数，不满足当前实现的统计校验及恢复要求。

本报告中的GB为10^9字节，GiB为2^30字节。数据库占用含表、TOAST及索引；对象元数据引用字节不等于桶物理字节。运行热盘、开发工作区、远端存储和异地备份分别计量，不能将备份移到另一目录后宣称项目总存储已经减少。

## 三、现有架构哪些数据是必要的

1. `services/api/app/ingestion.py`和`quote_ingestion.py`已按稳定赛事/盘口键更新当前投影，未将每次报价都写成独立永久历史。但不同盘口线、不同选项、过期赛事仍会累积；“current”表名不代表它自动淘汰旧行。
2. 当前行情可保留最新值；全站逐秒变化没有永久留存的业务必要。只需要在推荐接受、结果确认和结果修订等证据节点做不可变快照。完整审核/工具过程可热留三天，涉及未解决或质量复核的任务进入有期限的异常保留区。
3. 推荐长期最少需要稳定专家编号、来源和消息版本、运动类型、赛事最小摘要、推荐意图、期间、方向、盘口线、推荐时系统报价和时间、滚球计分基线、原文/原图、接受的工具证据、赛果版本、逐条结算及计算理由、统计重置边界。正确率汇总为可重建投影。
4. `expert_statistics.py`当前会校验不可变报价、最新有效赛果及结算台账，并通过赛事表区分足球/篮球、通过原文表筛选来源。删除赛事或原文后只保留统计数值，会破坏这些功能；现存外键也会阻止部分删除。
5. `v2_review_market_reads.quote_id`直接引用当前盘口。本轮读到114177条市场读取行、47729个不同盘口引用。不能在清理全部过期盘口时绕过外键；需先将需要永久保留的已接受读取证据固化，其他终态审核按完整依赖图清理。
6. 需要继续处理的消息版本、相册、回复、编辑删除事件、任务租约、检查点、去重/删除墓碑有各自生命周期。把它们一律三天删除可能使旧消息重新回补、漏掉编辑或丢失待恢复任务。

### 三天留存的准确边界

| 数据类型 | 建议规则 | 必须保护的例外 |
| --- | --- | --- |
| 完场/取消的普通赛事、关闭盘口 | 先确认终态，再从终态确认/最后有效更新算72小时；分批清理 | 推荐、结果、未完成审核或其他长期证据的引用 |
| 未开赛和进行中赛事 | 保留最新投影，按上游再次核验状态 | 不能因为开球时间过了三天就当作完场；未来赛程不能按接收年龄误删 |
| 普通TG发言及冗余版本 | 审核终态、媒体任务完成后，至少从最后接收/编辑的有效时间保留72小时 | 被推荐、引用回复、未解决审核、待恢复任务及质量事件占用的原文/原图 |
| 原始审核trace和搜索候选 | 三天热查；必要接受证据脱离临时搜索过程固化 | 活动租约、待复核、统计证据和故障调查 |
| 专家决策、最小原文/原图和赛事摘要、报价、赛果/结算版本 | 长期保留，增量备份；统计可重算 | 不因正确率重置删除旧证据 |
| 检查点、紧凑去重与墓碑 | 独立持久小表/分层索引，覆盖允许回补窗口 | 不直接套用聊天正文TTL |
| 用户与审计记录 | 各自生命周期和恢复约束 | 不随比赛或聊天TTL清理 |

实测88630条原文中，按posted_at三天内只有2345条；有593条原文被推荐引用，其中395条早于三天。70058场赛事中450场被推荐引用，其中313场早于三天。直接删旧原文和旧赛事会触及这些证据。

另有7788场仍标记live、4064场仍标记scheduled且开球早于三天。它们是状态核验缺口，不能简单按时间删掉来“解决”。已有活动异常需要重新取得上游最终状态，并确认无未结算/未完成依赖后再进入留存判定。

## 四、增长率与30–50 GB预算

按完整UTC日而不是当前尚未结束的一天计算：

- 11月4–10日按原始posted_at：平均749.6条发言/天。
- 11月5–10日按决策created_at：平均115.2条决策/天。
- 同期按原文入库created_at约数千条/天，显著大于新发言，说明历史回补仍在影响入库量；不能将入库量直接当作新增聊天增长率。
- 当前四类核心证据已分配5.194 MB，约5627字节/决策（含索引、现存修订和页空余）。按当前规模线性外推，一年约0.237 GB、三年约0.710 GB；不含原文、媒体、额外审核轨迹和未来schema变化。
- 当前推荐相关已知媒体60.617 MB/923条决策，若相同比例持续且去重行为相同，约2.76 GB/年。该推算不是图片增长上限，未来图片尺寸、重复率、群数和决策数变化会使它失效。

这说明持久化逐条决策本身成本很小，图片、全站盘口、索引、备份和开发产物才需要明确预算。若决策和媒体永久增长，即便三天热数据保持稳定，整体空间也会线性增长；应每月重算未来12/36个月容量。

以下是**待验收的运行盘配额设计**，不是已测得的清理后占用：

| 分项 | 基础预算GB | 约束 |
| --- | ---: | --- |
| 当前赛事/盘口、三天TG/trace、长期结构化证据及索引 | 8 | 逐批过期及索引维护；需先测清理后实际稳定水位 |
| 三天普通媒体 + 长期原文/原图 | 4 | 仅对应当前规模约一年情景；更长保留需要从余量增加预算 |
| WAL、临时查询、轮转日志 | 3 | 配置预算及监控；不是天然硬上限 |
| 当前/上一版镜像、浏览器依赖、受限缓存 | 8 | 去重计量，不保留全部构建候选与测试数据库 |
| 日常运行与可复用空间余量 | 7 | 不分配给无限增长的缓存 |
| 基础合计 | 30 | 不含旧库和全量同盘备份 |
| 维护、恢复或更长证据周期的额外余量 | 20 | 目标50GB时使用；仍需逐项计量 |

优先采用50GB运行水位目标，比30GB有更可用的维护余地。若要求“旧库、全历史媒体、全部本地开发副本、全部备份也合计30–50GB”，当前证据已经足以否定：仅旧表就186GB。不能靠压缩正确率计数来解决。

| 旧模型数据隔离/未开始 | infra/recovery、docs；归属及全部引用评估、异地容量、具名恢复演练 | 优先研究新版独立库迁移或旧数据异地归档；不把旧全量备份留在50GB目标盘 | 版本、行数、引用、媒体、统计重建、备份可恢复一致；无恢复证据不删除旧表 |
| 开发与运行资源预算/未开始 | infra、tests、docs；逐容器/卷归属及其他代理活动 | 清单化测试资源租期、冻结副本和候选镜像；仅清理已确认归属且不活动的资源 | 保留运行/回滚/调查所需产物；其他项目和正在使用的测试资源不动 |
| 容量发布验收/未开始 | infra、docs；以上工作包 | 监控表+索引、WAL、对象/版本、镜像/卷、备份和增长率；设35/40/45GB预警水位 | 完成72小时回收稳态观察，再连续七天容量与统计核对；达到预算前不能宣称30–50GB已实现 |

现有`infra/recovery/retention.py`仅适用于具名隔离恢复库、下限30天；没有生产三天留存服务。不能把常量改为3绕过原恢复保护。当前超时的高基数查询也说明不能用定期全库JSON扫描实现生产回收；应维护明确引用并限定每批工作量。

删除行后应区分“数据库内部可复用”与“文件系统归还”。维护/重建需要独立空间和锁预算，不能假定删完马上得到相同大小的可用盘。WAL的配置预算也不等于硬配额。参考PostgreSQL16官方routine-vacuuming及runtime-config-wal章节；对象旧版本回收参考S3 Lifecycle文档。此处未执行维护指令或生命周期操作。
