# Telegram复核领取批量租约

- 当前目标：减少远端消息复核领取的串行数据库往返，不改变实时接收、信任映射、历史保留、复核频率或截止时间。
- 责任目录：services/api复核领取、tests真实临时PostgreSQL行为验收、docs证据。
- 前置依赖：E175已安全生效并在21:05:14–21:35:14完整观察中；候选只能独立worktree实现，不能改线上挂载或中断观察。
- 当前证据：claim_events已锁定和排序选择候选，但对每条单独UPDATE RETURNING租约；采集器RECONCILE_EVENT_LIMIT=3，一批有3次写入SQL。E173只读简单SQL客户端约123–289ms，不能当本接口的精确耗时；来源仍间歇503/超时，本次尚无证据证明它们的唯一根因。
- 缺口：已锁定同批消息可一次更新，但当前产生N次串行网络往返；必须保留每条不同claim_id及返回与原排序对应关系。
- 设计决策：候选选择和FOR UPDATE SKIP LOCKED完全保留；为每条生成独立UUID，用显式uuid数组unnest绑定事件ID与claimID，一次UPDATE RETURNING所有租约。按原选择顺序组装返回，不依赖UPDATE返回顺序；空批不写。仍在原事务中，失败全部回滚，不提高并发、租约30秒、批量限制或超时。
- 实现动作：拆出有界同批租约写入，校验返回事件完整性；复用所有旧反伪造/编辑/删除/短租约恢复和公平份额测试。
- 验收场景：不同消息ID与独立claim_id正确对应；选择顺序、近期/历史份额不变；并发领取无重叠；第二条触发异常时第一条更新也回滚；空批不发UPDATE。真实临时PG模拟固定网络往返比较旧新结果，测量仅作隔离数据，不承诺线上比例。冻结完整回归通过再构建；E175完整结束并官方对账后才允许安全部署候选与重新观察。
- 失败处理：原行为断言失败先修复、冻结重跑；不删积压、不放宽来源租约/审核信任，不通过提高超时掩盖故障。若无可观测收益或一致性不成立，保留当前线上实现。
