## 1. 问题（先测后改）

`web/app/app.js` 的比分页在 `scope=all` 下先用 `/public/matches?include_markets=false` 拿赛事事实，再用 `/public/match-summaries` 批量补盘口，并每 30 秒重载一次。行内 `renderMatchOdds` 实际只画：主盘口那条主线，加该线最多 3 个选项。接口却按 `_quote_summaries` 的契约每场最多返回 24 条，页面上绝大部分被丢弃。

改动前的线上实测（50 场，`http://127.0.0.1:3003`）：

| 指标 | 值 |
| --- | --- |
| 明文 | 506 673 B |
| gzip 传输 | 43 097 B |
| 返回报价条数 | 1 200 |
| 行内实际绘制 | 144 |

每次 30 秒轮询都要重新付这笔钱，且解压与 JSON 解析发生在移动端主线程。

## 2. 修复

接口增加向后兼容的形状参数：`GET /public/match-summaries?mode=row`。默认仍是 `full`，因此既有契约与其断言逐字节不变。

- `services/api/app/routes/public.py::_row_quotes`：一条 SQL 精确复刻前端的取数规则——先建与 `renderMatchOdds` 相同的 24 条窗口，按 `(market_id, line, selection)` 重排，取第一条 `is_main` 非 false 的报价（NULL 视为主线，与客户端 `is_main !== false` 一致），再取该玩法该线的前 3 条；同时用子查询带回该场**全部**当前报价数 `markets_total`。
- 响应带 `shape: "row"`；每场仍是 `markets` / `markets_total` / `markets_status` / `quote_fresh` 的严格子集，行形状永远是完整形状同一顺序的前缀。
- `web/app/app.js`：`loadMatchSummaries` 请求 `mode=row`；`renderMatchOdds` 改用 `markets_total` 判断“更多盘口 ›”是否值得出现——原先只有截断后的数组长度可依，行形状下必须由服务端告诉它真实条款数。

## 3. 正确性证据

形状缩小最容易出的错是“少画了”或“画错了”。两条独立证据：

1. **单快照 SQL 对照**：在同一份数据上分别跑完整算法与行内算法，105 | 105 | 0 | 0（两边条数、差集均为 0）。早先一次跨请求比对出现 17/15 的差异，是两次 HTTP 之间行情变动与小数格式化（`44.500` vs `44.5`）造成的，与本改动无关，已用单快照排除。
2. **发布后线上逐场比对**：同一批 50 场，`full` 与 `row` 两个响应比对，`markets` 前缀、`quote_fresh`、`markets_status` 全部一致，mismatches = 0。

隔离测试 `run_tests.sh … tests.test_async_score_summaries tests.test_response_cache_policy`：`exit=0`，Ran 13 tests，OK。其中新增两条：

- `test_row_shape_returns_exactly_the_quotes_the_row_draws`：行形状 ≤3 条、`markets_total` 等于全部条数、是完整形状的前缀、新鲜度与状态一致。
- `test_row_shape_rejects_unknown_mode`：未知 `mode` 返回 422，不接受任意字符串。

旧的 `test_summary_preserves_exact_default_quote_contract_and_selected_limit` 未改动且通过，证明默认形状没有漂移。

## 10. 仍存在的缺口

- 静态资源仍为 `Cache-Control: public, max-age=300`，文件名不带内容哈希。要吃到长期缓存必须先做资源指纹化，属于独立一步。
- `/api/` 仍统一 `Cache-Control: private, no-store`（`http_runtime.py::request_context`，有 `test_response_cache_policy` 守卫）。公开只读赛事若要走 ETag/304，需要一条显式的、经测试的豁免路径，不能整体放松默认值。
- 本轮只压缩了载荷，摘要轮询仍固定 30 秒；按页面可见性自适应间隔尚未实现。
- 未测真实移动网络与低端设备上的实际渲染耗时，仅测了同机请求耗时与传输字节。
