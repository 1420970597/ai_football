# 多群组实时审核的有界并发

更新时间：2026-11-09 17:06 UTC。状态：设计已记录，未修改生产容量。

- 目标：减少不同专家同时发言时等待模型槽的时间；总审核槽从2评估到4，保持同一专家跨群组的全局底线2、历史并发0。目标仍是原始发言到自然accepted回执不超过10秒，本工作不能单独保证该目标。
- 责任目录：infra的显式审核容量覆盖、tests的原生worker生命周期与真实临时库调度验证、docs的测量和发布证据。模型/网关、执行器、账户许可和资金限额不在变更范围。
- 前置依赖：已发布0bd55505审核器、真实多群组消息与租约、固定Hermes并发上限、数据库与服务资源测量；不产生测试资金请求。
- 当前证据：实际总槽2、专家底线2、历史槽0；多窗口32条/28条等集中审核存在数十至数百秒排队及模型回合。当前11来源均可同时采集，增加审核槽不能替代来源、租约、作者信任或盘口身份校验。
- 缺口：此前仅讨论增加容量，没有4槽原生run循环的接纳、补位、取消、共享客户端/资源释放证据；不得仅设置环境变量便称已优化。
- 设计决策：复用当前asyncio任务及跨进程数据库公平调度，不创建线程内第二套业务。单worker4槽低于固定Hermes现有10运行上限；同一专家仍受现有数据库全局预算约束，原有新消息优先、老消息防饥饿、未知HTTP结果与租约规则保持。仅使用项目显式Compose覆盖，不改变默认开发环境或用户投注模式。
- 实现动作：新增原生run循环有界并发/补位/取消测试；用具名临时PostgreSQL复验多群、全局同专家限额、取消、乱序、故障和公平性。独立4槽合成I/O比较只证明本地调度，不冒充真实模型或接单延迟；记录当前Hermes/worker内存及CPU后才准备受控交接。
- 验收场景：四条独立任务同时等待I/O，第五条不超额，完成一条立即补位；任务共享受限HTTP客户端；退出取消并排空全部任务、监听器及连接；跨来源/跨pool同专家不突破预算，历史不会占实时槽；只改变预定容量、原用户策略/资金开关/金额/权限不变；发布后完整30分钟原文/原图/工具/自然订单对账。
- 失败处理：保留真实失败码及资源/429/超时证据；有退步则有界回到原容量而不动用户开关，不缩短消息年龄门槛、不清任务、不填造新鲜报价、不补投历史、不用资金测试创造样本。

资源预算：沿用生产worker现有0.25CPU/512MiB、Hermes0.55CPU/2GiB；容量增加只影响异步I/O在途数。若实际峰值或节流证明预算不足，另记测量与变更，不默认扩容或修改共享网关。本地针对性测试限0.25CPU/384MiB，隔离PostgreSQL限0.35CPU/384MiB；不与四个高负载构建同时运行。
