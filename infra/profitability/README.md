# Settlement history check

Run `reconcile_upstream.py` in the executor environment with scoped, authenticated input on stdin. It queries settled order history for adjacent 12-hour UTC windows. The input contract is:

- `start`: timezone-aware first boundary. The last requested window must have closed.
- `windows`: an optional integer between 1 and 4. Defaults to 4. Use 1 to reconcile an individual window as it closes.
- `scope`, `base_url`, `request_id`, `origin`: the authorized account session accepted by `VenueSession`.
- `local`: order rows for that same account and binding. Each row requires `order_no`, `stake`, `payout`, `net_profit`, `settled_at`, and `booked_at`. Supply `placed_at` from the venue, `currency`, and `fees` when available and use null for unknown values. Use the provider's settlement time as `booked_at` when present and the receipt observation time otherwise. Include earlier placements that settled in the audited window. With no native settlement time, include `first_settled_observed_at` from the stored receipt for that order when available.

Supply the input through a private process pipe. The result contains counts, window boundaries, and error categories. It omits order numbers, account identifiers, credentials, and monetary amounts.

On the production Docker host, `bash infra/profitability/reconcile_live_window.sh <UTC start>` runs the single-window check through the existing API and executor containers. It uses the healthy session for the one account binding present in the order ledger and opens a read-only database transaction. Credentials and order identifiers travel only through the process pipe. The command can run after the boundary without changing the account, order ledger, or deployment.

The first four one-shot timers save their reports in the private reconciliation directory. Run `reconcile_due_windows.sh <fixed UTC anchor> <private reconciliation directory>` from the recurring timer to check any window closed for at least 350 seconds. Each invocation checks order history for at most one window, starting with the earliest missing report. When the primary reports exist, the next invocation rechecks the earliest incomplete scan, unmatched order list, or contradictory receipt without a saved retry. Contradictions include disagreements in stake, payout, net, fees, currency, or timestamps, and native settlement times that fall outside the window or precede placement. The retry goes to `<ordinal>.retry.json`, preserving the primary report. A failed command leaves its window eligible for another attempt. A complete scan with matching order lists and missing fee or currency evidence does not trigger this retry. The same fixed anchor determines every window boundary.

After missing reports and initial retries have been handled, the rolling timer can recheck a window among the five most recent due windows. The monitor snapshot in `../state/latest.json` must be fresh, refer to one platform and provider account, match the fixed bounds, and show more settled orders than the local counts in the initial and retry reports for that window. A partial or unmatched scan can still supply its local count. The first scan triggered by each higher count is saved as `<ordinal>.late-<count>.json`. Existing reports are kept, and a failed command remains eligible for a later attempt.

The production transient timer uses the UTC calendar `*-*-* 02,14:25,45:00 UTC`. The reconciliation directory retains reports across reboots. After Docker starts the project API, executor and monitor, run `bash infra/profitability/restore_reconciliation_timer.sh` on the host. It leaves an active timer in place. Registering a missing timer schedules an initial check after 15 seconds, then continues on the UTC calendar. It reads the fixed UTC anchor from the running monitor and uses the existing private report directory. Missed one-shot reports are recovered by the rolling task in order, one per run. The host must invoke this recovery entry point after a reboot because the timer is transient.

For the November 18 pilot also pass `--with-pilot` to restore the hourly fixed 24-hour cohort sampling and the half-hourly public Telegram preview sampling. It reuses the original start, directories, and private source pilot launcher. It skips preflight registration once the final report exists and skips preview registration after the pilot deadline on November 20 at 02:15 UTC. Recovery records actual observation times.

The check compares reported stake, payout, profit, currency and fees. `complete_page` describes the full scan, which reads up to three pages per window. It requires a consistent provider total matching the count of distinct valid settled orders. `pages_read` and `scan_issue` expose interrupted, repeated, or limited scans. `order_receipt_fields_reconciled` also requires a nonempty, one-to-one match with native placement and settlement times in chronological order, amounts, fees and one currency. The report counts mismatches and fields available upstream for possible recovery. Separate wallet evidence is required to establish fee treatment and the account-level net result.

`settlement_window_attribution_complete` checks membership in the requested window for a nonempty, one-to-one match. For a missing native settlement time, it requires agreement on native placement time and a stored settled receipt for the same order. Both bounds must be within the window and in sequence. `bounded_without_upstream_time` counts these orders. The missing native time remains visible and still prevents `order_receipt_fields_reconciled` from passing.

# Continuous snapshots

The monitor stores its first available observation of each closed window under `state/window-closes/<ordinal>.json`. Between normal five-minute polls, PostgreSQL shortens the wait when the next fixed boundary is closer. A failed poll retries after five minutes. The initial 48-hour file is linked from the fourth window's archive. These files survive the routine checkpoint rotation. After downtime the monitor also queries up to four windows beginning at the earliest unarchived ordinal per poll. The actual observation time remains in the snapshot, so a recovery sample taken after the boundary shows when the monitor obtained it. The current snapshot continues to reflect late receipts.

The same recovery entry point restores `ai-football-profitability-analysis.timer`, which publishes every hour at minute 55 UTC. Run `bash infra/profitability/collect_analysis.sh .runtime/profitability-watch` for an immediate production snapshot. Reports are private under `.runtime/profitability-watch/analysis/latest/` with time-stamped snapshots alongside `latest`. The Markdown summarizes results and the JSON retains aggregate diagnostics, individual failures, source timestamps and evidence digests. The analysis has no order submission step.

The API container runs the diagnostic SQL sequentially in a repeatable-read, read-only transaction. Each SQL statement has its own timeout and savepoint. The report renderer runs offline and reads existing monitor and reference archives. When the latest settlement snapshot was written after the database observation, it looks for the newest eligible checkpoint at or before the observation. Snapshots older than 11 minutes are marked unavailable. The recommendation and placement reports use the latest 48 hours, with an earlier 48-hour execution baseline. Replays leave a five-minute buffer between the placement cutoff and the observation time for acceptance receipts to reach the ledger. The source replay uses the preceding 28 days for candidate selection and the latest 7 days for later evaluation. Reference coverage uses the most recent available replay per label over the last 7 days, with smoke captures identified separately. It reports mapped REST depth, complete outcome groups, stream top-of-book observations, paired adjacent lines and settlement-basis status. The JSON retains counts by sport, phase, period and market kind. Provider receipts, wallet evidence and archived reference quote coverage retain their respective time and settlement semantics.

The scheduled reference replay applies the offline price rule per natural account preflight. It uses the native account check's local completion time and compares reference books by their original source timestamp and receive time. The private reference archive may contain a `pricing-approvals-<date>.json` list alongside the corresponding `fixture-bindings-<date>.json`. Each approval binds the fixture and native market ID, sport, phase, kind, period, line, score basis, handicap orientation or team side when applicable, and settlement scope. It records its UTC approval time, settlement and cost evidence references, upper cost per unit, positive required edge, Leyu feed origin, and each independent source's venue, feed origin, minimum book depth and exact market rule hashes. An approval recorded after the original decision cannot authorize its replay. Keep the approval artifact with the recap to verify the recorded digest.

The price rule uses complete same-line binary books, three mutually exclusive winner propositions, or two adjacent half-lines per source where applicable. The price decision requires two independently reviewed sources with matching terms and usable depth. Reference publication times and the local offer check must be within five seconds of each other. Live pricing also needs confirmed period, scores, and red cards for the offer and references. The currently captured score-only observations can corroborate a score but supply no such complete state. Replay records eligible prices, below-floor prices, and why inputs failed. It leaves account permissions and order submission to the existing services. A computed floor measures the approved quote assumptions and expense limit. Use actual settled receipts to evaluate the resulting policy.

Order snapshots and their health timestamp are written independently of optional wallet samples. A wallet query error is recorded in `state/last_wallet_failure` until the next successful wallet sample.

For each settled order the monitor compares the projection to the latest stored settled receipt. The window includes aggregate counts of missing and inconsistent receipts. Four-window verification requires the same platform and provider account, one known currency, and verifiable costs. Apply `grants.sql` when updating the dedicated monitor role. Snapshot output contains neither order identifiers nor account identities.

If an order has no native settlement time, the observed receipt timestamp still groups it for diagnostics. Every closed window overlapping the possible interval, from the earliest recorded placement bound to the observed receipt, remains unverified. An overlap count can include the same order in successive windows. Its receipt amount is counted only once in the diagnostic totals.

`undated_settlements_bounded_within_window` counts overlapping orders whose earliest local placement bound and first matching settled receipt both fall inside that window. The receipt must carry the same native placement time, which must precede or equal receipt observation. The count indicates that the available timing evidence is confined to one window. Verification still requires a native settlement timestamp.

The snapshot also marks closed windows unverified when an unresolved submission could predate the cutoff, or when an accepted order still lacks a settlement receipt and the latest fixture result available by that cutoff was confirmed or void. The accepted-order check concerns completeness of receipts. A fixture result does not establish a wallet movement or a settlement timestamp.

Run `window_evidence.py` in a Docker Python image under the UID authorized to read the private archives. `collect_window_evidence.sh <private monitor root>` archives this summary as `window-evidence/<UTC timestamp>.json` under the monitor root. Before publishing a digest-named archive, the rolling job verifies that the completed scan reports the selected digest and the same 12-hour bounds. A ledger update between the monitor snapshot and the scan can yield a different digest. The job discards that draft and exits with status 75, leaving the next run eligible to check the ledger version visible in its fresh snapshot.

It is stored as `<ordinal>.receipt-<digest>.retry.json`, alongside the first scan. The summary prefers complete receipt reconciliation, then a scan with the matching digest and order list. Missing fee or currency evidence without a discrepancy does not itself trigger the retry.

# Execution price diagnostic

Run `execution_quality.sql` with `psql -XqAt -v ON_ERROR_STOP=1 -v anchor=<UTC event boundary>` using authorized read access to a single account's order, signal, settlement and quote records. It emits the preceding 48-hour baseline and up to the first 48 hours after the anchor. It keeps all settled orders in the totals. The preflight evidence must identify the same signal and execution attempt and fall between the recommendation and native placement times. The recommendation comparison uses matching contract fields and accepts a live basis resolved in the matching settlement record under a verified Leyu rule. The verified remaining-period rule also requires agreement between the recommendation, preflight, and submitted score baseline. For comparable orders, the report reconstructs amounts at the recommendation, preflight and fill prices and reports the two price deltas and the remaining difference to receipt amounts. Receipt net outside that comparison and the count of missing receipt net values are reported separately. A residual can flag a payout or settlement difference and alone cannot identify its cause. These results are diagnostic and do not count toward the real profitability target.

The cohort and window totals also break each stage into lower-odds counts and signed adverse and favorable deltas. Lower odds can leave a losing or void order's return unchanged. Each signed amount is null when no comparable order contributes in that direction. With comparable orders, the two signed amounts add to the stage delta when absent directions contribute zero. Sums use the same rounded per-order return amounts as the existing stage totals.

For a closed window, set `-v analysis_end=<exclusive UTC settlement boundary>` and optionally `-v receipt_as_of=<inclusive UTC receipt observation cutoff>`. The observation filter applies to current receipt projections. Later receipt replacements or result revisions can change a rerun, so preserve the original report alongside the close snapshot.

`windows` reports price attribution for each nonempty 12-hour settlement window aligned with `anchor`. A booking exactly at `window_end` belongs to the following window. `closed` indicates whether `analysis_end` reached the end of that window. `window_price_bridge_exclusions` reports the same evidence gaps for each window. Both outputs include the prior 48-hour baseline and preserve the existing cohort summaries.

`price_bridge_exclusions` reports the first failed evidence check per order, grouped by sport, phase, market, period and stored signal settlement reason. The settlement reason comes from the recommendation ledger. It can identify a missing final result or an existing ledger calculation alongside the first failed check. The breakdown includes all orders outside the price calculation and retains their receipt net where available. Its counts and amounts can be checked against the cohort totals.

`preflight_direction_outcomes` compares settled automatic orders with a complete price bridge by preflight price movement relative to the recommendation. Live rows require identical known full-match scores at both points. It reports receipt net, stake, distinct fixtures, cost-field gaps and the price contribution, aggregated by cohort or 12-hour settlement window. The comparison requires one account binding and no conflicting currencies across the automatic-order sample. This historical population differs from the prospective snapshot cohorts, which use recommendation creation time and require a full option snapshot.

The same report counts fixtures with positive aggregate receipts and shows each group's receipts after excluding its highest-receipt fixture. All comparable orders in that fixture and group are removed together. Groups covering only one fixture have no remainder. This check measures concentration and uses unadjusted receipts.

For each direction group, recommendation-price reconstruction plus the two price deltas plus `settlement_residual` equals `receipt_net`. The residual is the difference between recorded receipts and reconstruction at the filled price. It can include rounding and settlement differences and does not identify fees by itself.

The diagnostic reconstructs existing equivalent-outcome settlements under the same result version for Leyu period totals (native markets 2 and 18) and full-time live handicap (native market 4). The stored calculation must match the recommendation inputs and confirm the result. A matching submission permit must link to the preflight, and the latest settled receipt must match the native order and receipt net. Handicap reconstruction also requires the original provider-home line convention, matching effective stake, and agreement on the remaining-period score between the recommendation, preflight and permit. Separate report counts identify the two groups. The diagnostic does not modify recommendation, order, or wallet records.

# Fixture exposure replay

Run `fixture_exposure.sql` with `psql -XqAt -v ON_ERROR_STOP=1 -v begin=<UTC start> -v split=<UTC cohort boundary> -v end=<UTC end> -v observed=<UTC receipt cutoff>` using read access to orders, fixtures, expert signals and receipts. The replay compares no cap with a cap of one or two open fills per fixture for new automatic orders. All sports and markets are included. Manual and pre-period fills remain in the exposure. A matching accepted, unsettled or settled receipt confirms the fill. A fill releases its slot once its first settled receipt was observable. Fills with no such receipt stay open at the evidence cutoff.

Inspect coverage, tied timestamps and unresolved outcomes before interpreting the figures. The aggregate requires a single account binding and rejects mixed known currencies or incomplete fill evidence. Missing fee or currency fields are counted separately from receipt net. The counterfactual reuses existing fills and misses rejected or unsubmitted opportunities, rescheduled orders, and changes to remaining account budget. Treat the output as a concentration diagnostic.

The `fixture_sensitivity` rows summarize observed receipt net by fixture in the same placement cohorts, overall and by recommendation phase. The lowest and highest net are obtained by removing one fixture with observed receipts. The range is null when fewer than two fixtures have a net. `fixtures_missing_any_net` includes fully pending fixtures and fixtures with both settled and missing receipts. In the phase rows the calculation removes only that phase's fills for the fixture.

The `cap_sensitivity` rows show the observed receipt difference from each exposure limit. A positive delta means the limit excludes a net loss on the currently settled fills. The bounds remove one affected fixture with observed receipts at a time. They are null when fewer than two fixtures have observed deltas. The output separately reports the count and stake of excluded orders without a net receipt. For a fixed placement cutoff, `fills_without_observed_acceptance` identifies orders whose native acceptance was unavailable at the observation cutoff.

`same_side_comparisons` replays a limit of one concurrent order sharing the fixture, phase, native market, period, score basis and direction. Different lines compete for the same exposure budget. Pre-existing orders and manual orders count against the budget. Missing contract fields are counted and leave the order in the replay. A settlement receipt observed at the next order's placement time leaves the prior order active for that comparison.

Run `order_overlap.sql` with `psql -XqAt -v ON_ERROR_STOP=1 -v begin=<inclusive UTC placement start> -v end=<exclusive UTC placement cutoff>` to audit actual native fills. The automatic report runs it for the latest 48 hours. It compares each fill to earlier fills on the same account, provider identity, fixture, native market, period and direction, including earlier fills outside the report window. It uses full-period rules for verified Leyu football totals and the score baseline for remaining-period markets. Same-line counts include manual fills and previously settled contracts. Adjacent lines count for automatic fills while a prior contract is still open, within half a goal in football or one point in basketball. Receipt evidence must refer to the original order and be observed strictly before the later placement to close that prior contract in the audit. Each measure counts affected later fills independently. Missing placement or contract evidence, reused receipts and ambiguous pair ordering are reported separately. A zero count describes the sampled fills and gives no count of rejected reservations.

The `verified_period_total_comparisons` rows group the same line and direction across scheduled and live phases for verified Leyu football period totals. Native market 2 uses the full match and market 18 uses the first half. Full-period terms group together, including an unknown basis where the established native settlement rule supplies it. Other contracts remain in the cohort and count in `fills_without_group_key`. This replay measures overlapping economic exposure using the original fill order and the first recorded settlement receipt.

# Source and author holdout

Run `source_holdout.sql` with the same four UTC parameters as the fixture exposure replay. It covers filled automatic orders across all markets. A source or a source and author pair qualifies for a replay exclusion if its earlier fills span at least 20 settled fixtures and three UTC placement dates and have a negative sum of net receipts per unit staked. Only settled receipts observed before the split inform that exclusion. The later cohort reports realized receipt net, settled stake, and equal-stake return by phase and in aggregate. A zero exclusion count means the training sample did not trigger the rule. The fills represent the existing policy's accepted orders, so the replay omits opportunities that the original policy did not submit or fill.

The two persistent-loss comparisons additionally require at least five distinct settled fixtures and negative equal-stake receipt net in each half of the training placement interval. The midpoint comes from the supplied training dates. These rows are retrospective comparisons of retained real fills.

The fixture-loss comparisons start from the original source and source-author exclusions. They additionally require at least 20 distinct training fixtures with usable stake and net in the receipts available at the split. Each fixture contributes the mean of its order-level returns per unit staked. The resulting sum must be negative after removing the lowest-return fixture.

It adds the requirement that the recommendation-time snapshot has the same identity as the signal, the latest official result and signal settlement agree, and the recorded payout is within 0.01 of the reconstruction at the fill price. The report separates each failed check. For eligible fills it reports the estimated quote margin drag and the price movement effects from recommendation to preflight and from preflight to fill. Amounts require a single binding and at most one known currency. The comparison uses gross payouts and a hypothetical normalization of the original Leyu option set. Fee and currency gaps remain visible, and the report gives no estimate of available prices from independent venues.

`payout_conflicts_with_native_cancellation_return` counts conflicts with full principal returned, zero receipt net, and a matching latest settled receipt with native cancellation fields. It is a subset of `payout_conflicts_with_reconstruction`. The count leaves the provider's cancellation reason unclassified and the original receipt amounts in place.

# Recommendation opportunity coverage

Run `opportunity_coverage.sql` with `psql -XqAt -v ON_ERROR_STOP=1 -v begin=<UTC recommendation cutoff>` to count all saved recommendations alongside the recorded automatic order states for the unique ledger account binding. Counts use the recommendation as the unit, including withdrawn recommendations and those with no automatic order. Manual orders do not contribute to automatic order states. An absent order does not identify why execution did not occur, or whether the recommendation was eligible at the time.

The `competition_demand` rows group recommendations by sport, local competition ID, phase, market, period and scoring basis. Rows without a competition ID retain the local name where available. The display name for an ID uses one of the names currently recorded in the fixture projections. `automatic_fills` counts recommendations with an accepted or settled automatic order for the unique binding. These counts describe the local contracts an external feed would need to cover. They do not show whether a feed offers those competitions or an equivalent contract.

`automatic_order_stops` reports cancelled and rejected automatic orders by recorded reason, phase and contract. It counts order rows, including a cancelled attempt for a recommendation that also has a successful order. Missing reasons are marked `unrecorded`. Reasons outside the known service codes are counted as `other_recorded` without exposing their contents. Recommendations with no automatic order remain in the separate coverage totals.

For a completed period no longer than 48 hours, run `docker exec -i ai-football-v2-api-1 python - <UTC begin> <UTC end> < infra/profitability/no_order_evidence.py`. It requires the deployed `app.signal_identity` implementation and a single identifiable ledger account. It checks for same-intent orders, withdrawal by recommendation time and an original Telegram post already older than five minutes. For sport scope, it reads the last audited authorization for the account before each recommendation. The scope must have remained in effect through the recommendation's deadline and either agree with the current setting or have been superseded by a later authorization. It records football team totals separately because the current dispatch does not support that contract. Cases with none of this evidence remain `unconfirmed`.

`same_intent_order_evidence` counts the recommendations in those groups by their strongest order evidence at observation time. Native acceptance requires a nonempty native order number and an accepted or settled state. Pending, submitting and unknown states remain unresolved. Cancelled or rejected orders without a native receipt are reported separately. The exact original dispatch decision requires its own trace.

`expired_source_stages` uses the same message version's Telegram event and the successful review attempt identified by the immutable recommendation quote. It reports the five-minute deadline crossing, and counts prior model-provider failures recorded between the first and successful claims. Missing or unordered traces remain unverified. Telegram edits use original posting time for the order deadline.

# Private wallet observations

Install `install_wallet_observation.sql` as a database administrator in a single transaction after confirming the production order ledger has exactly one distinct account binding and provider identity. The security-definer function exposes only that account's available balance and observation timestamp when the active binding is healthy and its provider identity matches the order ledger. The monitor role receives function execution only, without account-table column access.

The monitor stores five-minute samples under its private runtime directory and keeps 72 hours. Each sample carries the time the executor observed the balance response, the balance age, and a freshness flag. Balance is fresh only when the observation is no more than ten minutes old and is no more than sixty seconds in the future. These samples reveal unexplained available-balance movement when compared with dated receipts. A full account reconciliation requires wallet statement entries, including currency and fee evidence.

Run `wallet_cash_flow.sql` through the monitor role with `wallet_samples` set to a base64-encoded JSON array of the private observation objects. Pass the variable and SQL through stdin to avoid placing observations in process arguments or shell history. Use only samples from the same account binding. The report aggregates stake debits and payout credits between successive fresh samples using native order timestamps. Pending settlements, undated movements, and sampling gaps limit the comparison. Its numeric differences are private and its status is diagnostic.

The rolling reconciliation timer also archives a private `<ordinal>.wallet.json` report using `reconcile_wallet_window.sh`. The report includes the requested UTC bounds, the first and last usable observations, the uncovered lengths at each boundary, and the diagnostic for each intervening interval. The comparison summary includes both the signed difference and the sum of absolute interval differences, so offsetting movements remain visible. For the dated evidence between those observations, payouts minus settled principal gives `settlement_net_from_payouts`. Settled principal minus principal debited gives `net_principal_released`. Their sum is the cash flow from the dated orders. The derived amounts stay null if a dated order lacks a required amount or there are no intervals. Each invocation handles one pending wallet report, starting with the most recent closed window and looking back up to five windows, including that window. A wallet query failure is retried independently of the order history result. An official wallet statement is still needed to determine fee treatment.

For an order without a native settlement time, the comparison can attribute its payout when the native placement and earliest matching settled receipt observation lie strictly within one sampling interval. The receipt must agree on order number, native placement, stake, and payout. The report counts these as `bounded_settlements` and retains the missing-time diagnostic. Previously archived reports reflect the query version used when they were written.

For each dated settlement with a provider-reported net, `receipt_net_difference` compares that amount to payout minus principal. `absolute_receipt_net_difference` sums the individual absolute differences, including offsets within one interval. The report counts comparable orders and mismatches. Missing amounts and locally derived net values are excluded from this comparison. Use the resulting differences to locate orders for statement reconciliation.

The cash-flow sums assign dated orders to intervals open on the left and closed on the right. An event at either sample timestamp makes that interval ambiguous because the event and the balance read may have occurred in either order. The report distinguishes unknown submissions from accepted orders awaiting receipts and counts affected intervals separately. One order or boundary can affect several intervals.
